## 2. Contract architecture and cross-feature boundaries

The architectural `Browser UI → authenticated API/application service → durable relational DB` pattern is documented in the **globally DRAFT System SDS**. F-02 and F-03 use the existing F-01 React/Express/PostgreSQL/`pg` implementation and server sessions within their separately reviewed scopes; this does **not approve** a global stack/deployment policy for all features. F-01's real role/session checks protect every other feature. **F-02 owns BR-08 Create/Publish validation** as well as Workshop DRAFT/PUBLISHED transitions: independent Create **AC/STS-F02-10** and Publish **AC/STS-F02-11**. F-02 implementation is delivered by PR #14 / Issue #12. F-03 depends on a valid F-02 published workshop, owns registration invariants (**BR-07 eligibility, BR-08 absent-deadline default + defensive fail-closed for malformed persisted PUBLISHED data**, AC/STS-F03-12/13), ACTIVE uniqueness, capacity and real-DB concurrency; local implementation/tests are recorded under PR #15. F-03 **does not own Create/Publish validation**. **Manual closure BR-10 belongs to Sprint 2 F-05/F-06**, including its own AC/STS in a later contract. F-04 reads persisted registrations within Participant or Organizer ownership; it does **not** implement F-05 cancellation or F-08 check-in.

**Sprint 1 vertical-slice acceptance (plan, not a fifth Feature):** Organizer logs in → creates/publishes eligible Workshop → Participant logs in → sees published detail → creates one persisted ACTIVE registration → sees own registration → owning Organizer sees matching roster; negative tests reject duplicate/over-capacity/concurrent final seat/unauthorized ownership. F-02 is merged and F-03 has local implementation/test evidence under PR #15; the full vertical slice remains incomplete until F-04 delivers Participant/Organizer registration views. Relevant code PRs must show applicable build/automated tests on their SHA from Sprint 1; Lab 5 hosts CI/CD/Docker/GCP expansion (NFR-06).
